# 需求、标注与证据

核对实现和组织标注数据时读取。这个模型用于避免重复计数、过度宣称完成与前后表述不一致；可以按当前项目简化，不要求逐字采用字段名。

## 分开保存四类对象

| 对象 | 需要保留的信息 |
| --- | --- |
| 需求 | 稳定编号、业务要求、当前事实、缺口、需求来源 |
| 画面状态 | 页面及状态编号、所属页面／上级入口、原型链接或文件、截图或重建范围、采集日期 |
| 标注 | 所属画面、关联需求编号、标注范围和完成阶段、颜色、画面位置、已有能力、缺口、配合角色、下一步、证据引用 |
| 证据 | 来源路径或链接、日期、验证对象与范围、结果、未验证边界；必要时记录版本或文件摘要 |

画面标签、展开详情和清单应读取同一份需求与标注数据，不分别维护多份文字。允许一条需求关联多处标注，也允许一处标注解释几条紧密相关的需求。

例如，某任务页同时有“查询接口已本地验证”和“业务结果分类待产品确认”，可以关联同一个需求编号；这是两个不同范围的标注，不是两个独立完成的需求。

## 完成结论需要与证据处在同一层

| 已有证据 | 能说明什么 | 不能据此说明什么 |
| --- | --- | --- |
| 原型有控件／示例数字 | 产品设计了该表现或交互 | 实际代码存在或数据可用 |
| 源码有通用接口、旧项目模块 | 有可参考或复用的基础 | 已适配当前项目和需求 |
| 当前需求代码存在且调用链明确 | 对应范围已编码 | 已部署、真实取数正确、页面已联动 |
| 隔离测试、编译或接口测试通过 | 被测范围在记录条件下通过 | 现场服务、真实权限和产品验收通过 |
| 指定版本的真实联调／验收记录 | 记录内明确覆盖的行为通过 | 未覆盖的页签、状态或其他环境也通过 |

优先读取已有最新证据。发现源码比证据更新时核查相关变化，必要时比较现有文件摘要；不把某次历史通过自动套到所有新改动上。没有摘要不意味着记录无效，也不需要为每次标注建立全仓库审计。

相互矛盾的证据保留差异：原型和接口字段不一致、旧注释与新规则不同、示例数字不能对账，都应说明需要核对之处。用户已明确确认的业务结论可作为依据，但不能由它推导出未执行的测试结果。

## 缺口如何写才有用

- **产品决策**：说明哪种含义或选择未确定、影响哪块界面；写清已有候选方案，但不默认批准一种。
- **外部数据／接口／环境**：说明缺少的字段、关联标识、样例、测试条件或资源，谁提供以及补齐后要验证什么。
- **内部待实现**：说明已有前置以及现在要补的组合、计算或交互；不要当成外部卡点。
- **仅缺源码或证据**：说明检索到的范围和未知点，写待核实。其他项目的同名模块不能作为本项目完成证据。
- **外部负责或冻结**：保留供数、承接和验收边界，不从需求清单删除，也不改成完成。

把“现在能做的部分”独立表达。例如，真实地图坐标尚缺时，可以先组合已有 ID 与配置并返回缺失标记；这一蓝色节点只指组合逻辑，不能说地图展示可以直接完成。

## 交付前核对覆盖

自动检查能自动检查的关系，再人工判断语义：

- 需求编号唯一；每条目标需求都能在标注或明确的非画面规则区找到。
- 每处标注引用的需求、画面和证据存在；背景复用不会增加需求总数。
- 页面、展开状态和标注的数量分别表述，不能都称为页面数。
- 每个绿色标题都有支持相同范围的证据；每个蓝色都有可独立执行的下一步；每个橙色都说明缺口。
- 不因一处有绿色基础能力，就把关联的整个需求归为已验收。
- 项目内证据链接有效；对外转发时，明确哪些链接需要原工作区。核心结论应直接可读，不能依赖接收者打开本机路径才能理解。

没有可靠工时权重时，报告需求数与明确范围的工作块即可。若需要比例，先说明分母、分类方式与部分完成如何处理，不能把代码量、标签数或阶段数量称为项目完成率。
