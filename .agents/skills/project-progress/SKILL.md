# 项目进度与卡点盘点

让接手项目的人看清：要交付什么、现有成果做到哪一层、现在能做什么、还差谁提供什么，以及这些工作如何连接。默认结合逐项清单与状态流程图；用户只要其中一种时按其要求交付。用人能理解的业务名称，不用文件名或技术术语代替功能。

## 先确认盘点对象

从对话、项目约定和现有资料确定根目录、目标版本、需求范围及当前承接职责。能查到的事实先自行查，不把仓库路径、代码是否存在等问题交给用户。需求边界确实影响结论且无法查清时再问，同时继续不依赖答案的核查。

- 优先复用现有需求编号、里程碑、验收表和文档入口；不预设项目有前后端、特定目录、接口平台或实施工作区。
- 以用户确认的交付目标为范围。当前阶段任务不自动缩减最终需求，旧计划也不能扩张用户范围。
- 原型类项目遍历目标页面及其全部下级页面、弹窗、页签和关键展开状态；非界面项目沿业务流程、命令、接口、批处理或用户旅程展开。
- 共用交互、基础服务和跨模块依赖单列，避免重复计数。外部负责和冻结项只要仍在需求内就保留。
- 没有正式需求时整理候选清单，区分用户明确要求、已有资料及待确认推断，不把源码现状反推成全部需求。

## 把需求和证据对上

先读已有盘点，再核对影响结论的需求来源、实现入口、调用关系与验收记录。找不到源码时说明检索范围和未知点，不能直接宣布该功能没开发。

每个独立可验收结果有稳定编号。记录当前表现、实际证据、主要缺口、可以先做的工作及承接关系。详细字段和冲突处理见[清单与证据口径](references/inventory.md)，需要建立或更新逐项清单时读取。

重点区分：

- **存在基础代码**：通用模块、旧项目实现、代理接口或数据结构可参考，尚未证明支撑当前需求。
- **编码完成**：对应范围有实现；编译、接口可见性、真实数据联调、页面联动分别记录，不能相互代替。
- **验收完成**：针对本需求和相应版本，有足以支持完成结论的结果。历史通过要带日期与范围，本轮没跑就不写成本轮通过。

用户已确认的分工或产品结论可以作为依据；团队责任、截止时间、数据来源和通过结果不能自行补全。原型、接口文档与实现冲突时保留差异及需谁确认，不默默选择最方便开发的一份。

## 判断卡点与可推进部分

先把技术核查与真正需要别人决定的事项分开：

| 情况 | 应说明什么 |
| --- | --- |
| 能在仓库或隔离环境查清 | 由技术侧核查的具体问题及检查办法，不包装成 PM 决策 |
| 需求含义、取舍或业务口径不明确 | PM 需要决定的具体问题、影响范围和已有选项；建议不等于批准 |
| 缺接口、权限、资料、设备或测试条件 | 缺什么、由哪类角色提供、补齐后怎样验证；未知负责人写待落实 |
| 等待本项目其他实现 | 标明内部前置步骤，不冒充外部卡点 |
| 仅缺证据或源码未定位 | 写待核实及所需证据，不断言功能不存在 |
| 外部负责或本侧冻结 | 保留供数边界、外部承接和验收闭环；不把冻结算完成 |

一个功能部分能做、部分卡住时，拆出范围清楚的工作节点。例如基础查询可先实现，而缺字段的数据接入和页面验收另列。不得用默认值、空返回、假数据或旧系统同名能力把卡点变成“已完成”。

准备工作可以标成可推进，但标题必须说明只是核查、设计或隔离验证，不能把依赖尚未齐备的完整接入标成可直接交付。

## 形成进度图

按[流程图与交付规范](references/flowchart.md)组织节点、连线、展开信息和校验。通常采用“已有基础 → 可并行推进的实现／待补条件 → 业务流程或页面树 → 整体验收”，按项目实际关系调整。

默认色义如下；用户明确指定其他颜色时跟随用户：

- **蓝色：所列范围现在可以直接继续推进。** 没有阻止这一步的待决策或待接入条件。
- **橙色：所列范围有卡点或尚待核实。** 写清 PM 决策、外部条件、内部前置或缺证据。橙色不等于整块工作都不能动。
- **绿色：节点注明的范围已完成，并在节点右下角放勾。** 只完成编码时，节点就叫“某接口编码”，不能叫“整个模块完成”。

同一编号可出现在局部实现节点和整体验收节点，但需求总量只计一次；图中节点数不是需求数。没有可靠工时权重时只报条目数，不把可推进条目占比、阶段数或代码量称为完成率。

## 更新和落地边界

沿用项目已有文档格式和唯一进度入口，图只作为带日期的进度快照，引用详细证据。清单可以作为图的展开项，无需再维护重复的独立进度表。仅要求会话展示时不强行新增仓库文档；要求保存时写入项目已有的文档位置。

发现需求无人承接或工作区重复时可以提出归并、补建建议；盘点和画图本身不授权改写活跃实施计划、归档工作区或删除文件。用户已授权的调整按现有项目规则完成，不再重复询问，也不借此启动产品开发、提交或发布。

复查时保留原编号和有依据的完成记录，注明状态变化的原因与日期；需求范围变化单独记录。需压缩旧记录时遵循项目的历史保存约定，不让新快照抹掉原始证据。

## 交付前检查

核对范围是否覆盖全部下级内容，编号是否唯一，主责是否遗漏或重复，状态计数是否与清单一致。每个橙色节点能回答“缺什么”，每个蓝色节点能回答“现在具体做什么”，每个绿色节点能追到相应范围的完成依据。

检查图中文字、连线、三色和右下角勾。交互图还需验证展开与收起、长文本和窄屏，修正遮挡与溢出。文档更新检查本地链接及差异；仅做盘点时不为给图盖章而顺带运行产品构建或现场操作。确有授权的验证按风险执行，并准确说明实际检查与未覆盖范围。

最终给清楚的阅读入口和一句可执行结论，不在图外重复整份清单。能力或材料不足时保留可用成果，指出具体缺口，不虚构完整盘点或已通过验收。
