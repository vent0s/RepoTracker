# 清单与证据口径

建立或更新需求盘点时读取。以下是最小信息集合，不要求所有项目都采用相同表头或新增数据文件。

## 一个需求条目要说清什么

| 信息 | 要点 |
| --- | --- |
| 编号与位置 | 复用现有编号；记录所属页面、流程或能力。新增编号保持稳定，不随排序重编号 |
| 可验收结果 | 写使用者能看到或系统能完成的变化，避免把文件、方法或泛称“模块”当作需求 |
| 需求依据 | 用户确认、原型版本及页面、需求文档位置、任务记录等；示例数字不是生产数据 |
| 实现与验证证据 | 仓库／版本、相关入口及调用关系、实际测试或验收记录；区分代码存在与调用方已接通 |
| 当前进度 | 没找到对应实现、待适配、已有编码待验证、部分验收或已验收等事实描述 |
| 缺口与下一步 | 本次能做的具体范围；需要的决定、数据、访问条件或内部前置 |
| 承接关系 | 主要工作区或责任角色；协作方可有多个，未落实的责任如实标注 |

简洁表格通常使用“编号｜需求｜当前进度｜卡点／下一步｜依据”，在条目或分组中补充承接关系。详情太长时放入可展开节点，避免把整张图压成小字。

## 从资料到结论

根据结论所需深度核查，不固定要求每项读取全仓库：

1. **范围证据**回答为什么它属于本次交付。原型有下级页面时继续展开，不把一个入口当作已覆盖整个流程。
2. **实现证据**回答对应逻辑在哪里、被谁使用。转发旧系统、注册模块、定义结构或出现同名方法，都不足以单独证明当前业务已完成。
3. **验证证据**回答在什么版本、环境、数据和日期下验证了什么。构建成功不证明运行或外部取数成功，测试替身通过不证明真实联调通过。
4. **现场或界面证据**只在需求确实包含这些效果时需要。没有界面的服务不强制套页面验收；有页面的需求也不能只凭接口完成就收官。

状态结论和证据时间分开。例如“当时通过编译、当前代码未复验”，而不是“今天已编译通过”。不同来源相互矛盾时列出冲突；没发现相关代码只能支持“在已检查范围内未找到”，不能证明所有仓库都没有。

## 两个维度，不混成一个百分比

**完成到了哪一层**和**下一步能否开始**是两件事：

- 一个接口已编码但缺测试访问条件：编码阶段可以绿色，真实联调为橙色。
- 一整页等待源码与缺失字段，但后端基础查询可实现：页面完整交付为橙色，范围明确的查询实现为蓝色。
- 内部算法尚未完成但条件齐全：其实现可蓝色，依赖其结果且当前不能开始的验收节点为橙色“待内部前置”。
- 功能状态未知：标橙色“待核实”，同时列出可以立即进行的技术查证；不把未知强行归为待开发或已完成。

在清单中保留细致的进度事实，在图中用三色表达节点范围。不要为了凑三色而丢掉部分完成、历史验证和外部负责等信息。

## 计数与归属

- 以独立可验收结果计数；实现任务、数据准备、页面显示和验收节点可能引用同一需求，不重复加到总量。
- 共用导航、刷新、权限或基础能力应按项目真实验收方式计数一次，不在每个页面重复增加。
- 若给状态数量，同一套计数必须互斥且总和等于需求总量；局部阶段完成不能把整条需求搬进已完成数量。
- 一条需求只有一个主要承接工作区／角色；共享供数和横向验收可以被多个条目引用。无人承接要明确列为缺口，不能为了表格完整而虚构负责人。
- 工时百分比需要有来源的估算与权重。没有这些依据时可以写“可直接推进范围”，不能把条目占比称为工程完成率。

## 更新已有盘点

先保留需求编号、版本、原完成范围和证据，比较变化：新增需求、范围调整、新增实现、新的验收、卡点解除或证据失效。只有与结论有关的事实变化才更新状态。

需求范围被批准修改时保留原要求及变更依据。依赖改版导致旧验收不再覆盖当前版本时，记录“旧版本已通过，新版本待复验”，不抹掉过去的完成记录。
