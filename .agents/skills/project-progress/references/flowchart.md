# 流程图与交付规范

绘图时读取。图要呈现流程与依赖，不能只是把进度表换成彩色卡片。

## 先选合适的结构

- 页面型项目：按原型入口和下级页面画树，保留弹窗、页签及深层页面的需求归属。
- 服务、工具或数据项目：沿输入、处理、外部依赖、输出及验收画流程，不虚构前端页面。
- 多条实施线：用并行分支表达可同时推进的范围，再汇合到联调或验收。工作区是承接关系，不天然等于业务顺序。
- 若同时画“业务导航”和“实施依赖”，分区或标明连线含义；不要把点击入口画成编码必须先后的关系。

优先呈现已有基础、当前可执行工作、具体卡点、最终交付之间的真实关系。没有因果或入口关系的节点不要随意连箭头。

## 每个节点保留的内容

节点上直接显示：业务名称、范围或需求编号、当前进度，以及一行可做的工作或卡点。完整来源、验收条件和逐项需求可展开查看。即使不点击，用户也应看得懂进展和主要阻碍。

聚合节点有未解除的交付条件时不能整体标绿。必要时拆成“编码完成”“离线验证可推进”“真实接入待条件”等节点；标题和色义必须针对同一范围。

## 状态外观

默认蓝色表示可直接推进，橙色表示有卡点或待核实，绿色表示相应阶段完成。每种颜色同时配状态文字，不能只靠颜色区分。

绿色节点在**自身右下角**显示勾，避免把勾放在整个画布角落或仅放在图例中。给勾预留空间，不遮住日期、说明和展开按钮。可以使用文本 ✓ 或环境提供的图标，不需要为此生成位图。

用柔和的状态底色、清楚的正文和中性的连接线；深色与浅色都应可读。图例应写明蓝色针对所列范围，绿色针对已完成阶段。保留盘点日期，避免旧图被当作实时状态。

## 选择输出形式

- 小型、静态、节点和连线已经足够表达：使用 Mermaid。
- 需求较多，需要节点展开才能同时保留概览与细节：使用交互图；只有当前环境提供时才使用其会话可视化能力，并读取相应技能规则。
- 需要独立导出或更精确的节点布局：使用当前环境支持的 SVG 或其他确定性绘图工具。

不依赖某个固定插件、操作系统、绝对路径或库版本。能力不可用时选可用的等价形式，必要时说明实际展示限制；不要声称未生成的图或未打开的交互已经验证。若 Mermaid 的渲染器不能稳定放置右下角勾，换用支持精确布局的形式，不把节点标题后的勾冒充右下角标记。

交互图只需能展开节点或需求详情，不默认增加搜索、筛选、编辑、导出等界面。静态与展开态共用同一份清单数据，避免手工抄写后丢项或数字不同。

保存位置服从用户请求和当前项目约定。会话展示不要求建立仓库网站，保存文件也不意味着需要发布到外部服务。

## 交付前检查

1. **覆盖**：原需求编号在图的节点或展开信息中能找到；共用项和外部负责项没有遗漏。
2. **颜色**：蓝色节点确有当前可做的范围，橙色说明具体条件，绿色有相应完成依据且勾在右下角。
3. **连线**：指向正确，分支与汇合符合实际，业务导航和实施顺序没有混淆。
4. **可读性**：长标题、卡点文本、图例、标记和连线不重叠；不靠缩小字号塞入一张大图。
5. **交互**：实际展开至少一个内容较长的节点，核对需求条数和详情；窄屏可读，收起后连接位置正确，没有运行错误。
6. **证据**：图上的完成和验证结论来自记录。对图的浏览器检查不是对产品的业务验收。

典型结论可以是“先推进这几块明确的开发，另一部分等产品或数据条件落实”，无需在图外再复制一遍所有节点。
