# workspace-gen

在当前仓库的 `devSchedule/` 下组织实施计划。让接手的人知道要完成什么、为什么这样做、怎样验证。规划文档不替代正式设计；用户另行要求实现时，才修改产品代码。

## 文件职责

```text
devSchedule/{工作区名}/
└── doc/
    ├── 里程碑-{工作区名}.md      唯一进度入口
    ├── 概述.md                   按需说明背景
    ├── harness.md                测试场景与验证办法
    └── 历史/                    需要保存压缩前原文时创建
```

- 里程碑回答进展、任务、完成条件和下一步；文件名必须包含工作区名，不新建泛称的 `里程碑.md`。
- 概述讲为什么做、当前事实、设计依据和依赖，不另列进度或下一步。
- `harness.md` 是验证说明，写清测试准备、操作、预期结果、关键约束和失败后如何检查。
- 常规工作区使用三件套。轻量工作区用里程碑承载简短验收，概述可省略；需要独立维护多组测试场景时再建立 `harness.md`，不链接未创建的文件。
- 历史目录按下方原文搬迁规则使用，不预建空目录。
- 每次创建或更新，同步 `devSchedule/README.md` 的索引摘要；唯一活跃进度仍在里程碑。

正式文档最终放到哪里，按仓库实际约定记录在里程碑。还没确定时写候选路径与缺少的决定，不虚构已经存在的出口文档。

## 先看项目现状

每次先读项目约定（如 AGENTS.md）和 `devSchedule/README.md`，再按主题读取相关设计、规范、脑洞根文档及代码。用 `rg --files`、`rg -n` 定位，只解释与本次任务有关的事实，不复制大段背景。

涉及路线判断或收官时，再读对应的重构状态、文档分层或收官规范；写验证说明时，再读项目的 Harness / 验收规范。重置或重构期间，冻结材料只作为历史，不能冒充当前实现。

从上下文确定工作区名、系统 / 玩法 / 工具等类型、期望结果、限制与正式文档去向；重要选择尚不清楚时才向用户确认。按实际复杂度选择常规或轻量形式，不为凑三件套制造重复内容。

## 写法与内容

开头先讲完成后用户或系统会有什么变化，再交代当前进度。路径、编号、技术名词服务于解释，不替代解释。首次使用可能陌生的术语时简短说明，已有 API、协议、参数、测试命令与场景编号保留准确写法。

用段落讲原因和条件，列表讲步骤，表格比较方案或场景。不要把每一阶段都写成相同的七八项表单；共同依赖、正式文档归属和验证约定集中写，阶段内只补特殊条件。

模板是参考结构，不要求生成所有标题。没有内容的风险、历史、迁移、覆盖层级等栏目直接省略。明确区分“已有实现”“准备修改”“已运行验证”“计划中的检查”，避免每段堆叠状态标签。

### 里程碑

常规计划组织为 1–6 个可执行阶段；轻量计划用 1–3 个阶段，并简短说明为何足够。每阶段让读者能回答：

- 完成后能观察到什么变化。
- 要改哪些行为，相关代码或文档在哪里。
- 需要哪些前提；共用条件链接到统一说明。
- 如何操作和判断成功，失败时先检查什么。
- 当前是待启动、当前推进、已完成还是历史参考。

验收场景已在 `harness.md` 详细说明时，用编号与链接引用；不把同一套步骤抄两遍。完成后写一句结果摘要；原文已搬迁的，附历史链接。阶段的正式文档去向与共同约定相同时无需重复。

先查清会影响后续实现的接口约定和依据，再扩展界面或内容；跨工作区的真实阻碍要说明影响，不只写“存在依赖”。

### 概述

背景确有必要独立阅读时再写。解释为什么需要这项工作、目前系统怎样运行、希望改变什么、哪些已有设计和约束相关。只有涉及其他系统、迁移或收官时才展开这些内容。进度与下一步仍由里程碑维护。

### 验证说明

`harness.md` 的标题可用“测试准备”“测试场景”“预期结果”“失败后查什么”“自动化进展”。每个场景需明确初始条件、操作、预期结果、必须保持的约束、可检查的输出和失败诊断；可以用几段连贯说明覆盖，不要求六个独立字段。共同准备与约束集中记录。

项目已有验收分层与命名时遵守；没有时按实际检查内容组织，不硬套 H0–H5。需要时区分文档 / 数据检查、业务行为、工具链、界面集成和兼容迁移等范围；仅规划的工作只需与其产出相称的检查。

保留实际测试命令、日志位置、场景 ID 和证据。尚不存在的自动化明确写为计划，不能宣称已通过。夹具是可重复使用的测试输入或环境；用到时说明来源，以及收官后哪些仍被代码或工具依赖、应放在哪里。

### 写作示例：计划与验收如何衔接

以下是虚构示例，不是当前项目的实施任务。示例假设事件已经有稳定 ID，开发环境已有通知发送器的测试替身。

```markdown
# 断网恢复后的重复提醒 — 里程碑

这次要让同一条事件在重连后重发时，只产生一次通知。新的事件仍需正常提醒。当前尚未修改代码；先核对接收记录和通知发送的先后顺序。

## 第一阶段：记住哪些事件已经处理

调整接收逻辑，在重复事件到达时查询处理记录；通知发送失败的事件保留重试机会。具体模块路径先从现有实现确认，不能假定项目已有去重表。

完成条件：SC-01 中重复发送同一事件不会多发通知；SC-02 中发送失败后仍能重试成功；SC-03 中不同事件各自收到通知。验证步骤见 harness.md。本阶段待启动。
```

对应 `harness.md` 可写为：

```markdown
# 断网恢复后的重复提醒 — 验证办法

## 测试准备

使用隔离的事件输入和通知测试替身，开始前清空这组测试的处理记录。记录事件 ID、处理结果及通知调用次数，不向真实用户发送通知。

## SC-01：重连后再次收到同一事件

先送入一条事件，确认通知成功，再模拟断线恢复并重送同一 ID。预期通知总次数仍为一次，重复接收在日志中可辨认。若次数增加，先核对事件 ID 是否变化，再查处理记录何时写入和读取。

SC-02 让第一次通知返回失败，再重送该事件，预期可以成功重试；SC-03 发送两个不同 ID，预期各通知一次。两项用于防止去重逻辑误吞失败重试或新事件。

以上场景尚未自动化。实现时复用项目现有测试入口，记录实际命令与结果，再更新本节状态。
```

## 更新已有工作区

先读里程碑，再按需读概述、验证说明和历史摘要。保留用户决定，变化用带日期的修订解释；不借结构整理替换另一份活跃方案。

- 同时存在正式命名的里程碑与旧 `里程碑.md` 时，停止迁移并询问保留方式，不自行覆盖或合并。
- 仅有旧文件时先重命名并修复链接，再按当前请求编辑。
- 从当前事实补齐缺失且需要的文档，不生成空壳。
- 实质覆盖另一份活跃计划，且当前请求未授权时，先确认。已明确授权的调整不重复询问。
- 对应脑洞收敛计划存在时，沿用转实施规则：整体标为“已移交·历史参考”，移除当前下一步并指向本里程碑。此后唯一活跃进度在这里，脑洞只回写待验证结论。

## 历史保存与文档维护

这些是维护规则，执行记录集中放在里程碑末尾，勿复制到每个阶段开头。

- 某阶段完成，或同一阶段的“补充”达到三条时，检查压缩；当前推进的阶段不压缩。改变活跃工作区结构前需有用户确认，已明确授权的整理不再重复询问。
- 压缩是无损搬迁：补充与已完成实录全文保存到 `doc/历史/{YYYY-MM-DD}-{主题}.md`，注明来自里程碑的原文。一阶段可拆多文件；先查历史摘要，避免重复搬迁。
- 里程碑保留阶段骨架、一句结果与历史链接，更新状态和顶层索引。历史文件长期保留，随工作区收官；Git 历史只是第二份保障，不代替原文保存。
- 更新日期、工作区类型、文档归属等维护信息集中放在文件末尾；当前任务状态仍在里程碑开头清楚表达。
- 收官后的稳定结论进入正式文档，devSchedule 不作为永久设计依据。

## 完成前检查

核对文件命名、目录链接、历史链接、阶段状态、场景引用和所用验收分层。运行 `git diff --check` 与 `git status --short --branch`；遵守项目约定。仅生成规划时不顺带启动本地运行时或产品构建，实际实现与验证遵循另行授权的任务范围。

交付先说明计划解决什么、怎样验证、还缺哪些关键条件，再给唯一阅读入口。无需逐项播报空目录或未发生的维护动作。不在未获单独请求时提交代码。
