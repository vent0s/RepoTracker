# brain-storm

帮助读者理解正在讨论的事情、各个选择的理由，以及还需要解决什么问题。输出是讨论与规划文档；用户另行要求实现时，才修改产品代码。

## 文件职责

```text
brain-storm/{项目名}/
├── 收敛计划-{项目名}.md        唯一进度入口
├── 脑洞-{项目名}.md            问题、正文目录与决定记录
└── 脑洞-{项目名}-{编号}-{主题}.md
```

- 收敛计划回答“做到哪里、接下来做什么”，是唯一维护执行进度的地方。
- 根文档简短介绍问题，维护一份正文目录和决定记录。不要再用“方案地图”和“拆分文档索引”重复列同一批文件。
- 拆分文档解释具体问题、方案与依据，回链根文档和父文档。编号继续使用 01、01-01、01-01-01；文件名默认用简短中文。
- 每次创建或更新工作区，同步 `brain-storm/README.md` 的索引摘要。摘要链接进度入口，不另建任务清单。
- 讨论材料留在 `brain-storm/`，实施计划由 `devSchedule/` 承接，稳定结论进入项目实际使用的 `doc/`。

## 先了解已有内容

先读项目约定（如 AGENTS.md）、脑洞顶层索引和相关工作区根文档、收敛计划，再按问题阅读正文、正式文档和代码。使用 `rg --files`、`rg -n` 定位，不为了填“上下文索引”扫描或复制无关内容。

从已有资料确定问题、讨论对象、希望支持的决定和用户限制。只有重要信息无法查到时才问用户；不重复询问已确认的决定。区分仓库当前事实、用户期望和外部资料能支持的判断。

引用已有材料时，在解释用到它的地方链接，标签写文档主题即可；索引中的路径以仓库根目录为基准，Markdown 目标按所在文件解析。不要给每篇短文附一张重复的相关文件表。新增或更新引用时，按下方维护规则刷新目标的最近引用日期。

## 正文怎么写

先用一两段讲清这篇文档的事情和目前判断，再展开理由。以下是需要覆盖的信息，不是必须逐项填满的章节模板：

- 为什么讨论这个问题，怎样的结果对用户有价值。
- 有哪些实际选择，各自解决什么问题、需要什么条件、代价在哪里。
- 当前倾向什么，依据是什么；没有足够依据时直接说明尚不能判断。
- 用户已经决定什么，还有什么需要决定或验证。

标题用具体问题，例如“换一台机器人后保留哪些记忆”，而不是只有“方案范围”“迁移边界”。任务自然写成“查清接口允许读取什么”“试试断网后能否恢复”等；不限制动词，但不要把脑洞任务写成未经授权的产品实现。

用段落解释原因和条件，用表格比较真正并列的选项，用列表写步骤。API、协议、参数、测试编号等准确表达照常保留；可能陌生的术语在首次出现时解释，不用含糊口语替换技术含义。

通过“用户已决定……”“资料表明……”“建议先……”“这部分还没测过……”说明结论性质，不在每段前机械堆叠标签。范围限制只写会影响理解或行动的内容，不反复声明无关的未做事项。

不要生成空栏目、没有内容的“边缘记忆”表，或每篇都附“是否继续拆分”。只有需要实际处理的问题才写出来。同一事实以一个位置为准，其余地方用短摘要和链接。

### 写作示例

以下是虚构讨论，示范清楚表达与技术条件可以同时保留：

```markdown
# 能不能先用家里的电表数据发现异常用电？

用户希望外出时知道家里是否出现异常耗电，并接受首次登录授权。建议先检查现有电表或供应商接口能提供什么数据，再决定监测方式；暂时没有理由先购买机器人。

如果能持续取得带时间戳的用量数据，可以比较平时与异常时段。若接口每天才更新一次，就只能做较慢的用量提醒，不能称为实时告警。接口文档和实际返回样本需要分别核对，不能仅凭 App 能查账单就认定第三方也能接入。

## 先查清什么

找一个允许第三方读取的接口，记录授权要求、数据间隔、单位和更新时间。用正常数据、延迟数据和授权失效三种样本检查结果：系统应区分“用量正常”和“暂时没有可靠数据”。

这些检查还没有执行。查清后再决定这个数据源是否值得继续投入；具体设备控制不在这次调查中。
```

## 怎样组织目录与进度

### 根文档

开头说明问题和当前讨论状态，接一份正文目录。目录按需包含编号、文档链接、内容、父级及维护日期；编号已清楚表达父级时无需重复一列。目录之外只保留理解当前讨论需要的决定、摘要和引用，不复制正文论述。

决定记录保留稳定编号、日期、内容、理由和影响。历史决定按发生时的语境保存，后续变化通过修订说明关联；不要把编辑措辞当作新的产品决定。

文档状态与日期放在末尾的“文档维护”部分，或根文档目录的相应列。没有折叠或边缘文档时，用一句维护结论即可。

### 收敛计划

开头直接说目前进展和当前下一步。按实际需要组织阶段，每阶段说明要解决的问题、要做的讨论或调查、产出和完成条件；共同规则集中写，不在每阶段重复。状态继续使用“待启动、当前推进、已完成、历史参考、已移交”。

正文说明“怎样才算讨论完成”，例如“能说明三条路线各自的主要阻碍和证据缺口”，而不是只要求某个表格填满。正式文档出口和移交条件记录在这里；未选定时明确候选和还缺的决定。

目录和 README 可摘要当前状态，但不得产生第二套维护中的阶段或下一步。文档体检放在收敛计划末尾，不占据进度说明的开头。

### 何时拆分

一个问题有足够独立的选择、证据或讨论，单独阅读确实更清楚时再拆分。超过 3–5 个独立方案方向、跨越多个系统职责，或约 1–2 页仍无法讲清，是检查拆分的信号，不是强制凑文件的指标。

根文档只保留短摘要和链接。拆分索引达到 24 篇时，收敛计划增加一次“是否整区收官或归档”的检查；归档仍须用户显式触发 `$archive-workspace`。

## 更新已有工作区

先读现有内容，保留用户决定与有效材料；本次请求已授权的调整直接完成，不因“已有文档”重复询问。

- 若同时存在 `收敛计划-{项目名}.md` 与旧 `里程碑-脑洞-{项目名}.md`，停止迁移并询问保留方式，不自行覆盖或合并。
- 只有旧文件时，重命名为收敛计划并修复链接，不借此重写已有决定。
- 若存在旧 `概述-脑洞-{项目名}.md`，将独有内容并入根文档或收敛计划后删除旧概述，修复引用。
- 缺少收敛计划时，从已有内容补建；不要把候选判断改成用户决定。
- 实质覆盖另一份活跃方案，且现有请求未明确授权时，先询问如何保留内容。普通补充与已授权编辑无需再确认。
- 对应开发里程碑已经建立的工作区，收敛计划整体标为“已移交·历史参考”，移除当前下一步并链接该里程碑；脑洞只回写概念与验证结论。

## 文档维护

以下规则管理文档的保留方式，不是每篇正文都要解释的产品内容。分层发生在工作区内部，不跨目录、不移入仓库 archive、不删除历史事实；正式 `doc/` 不参与降级。

| 状态 | 判断与处理 |
|------|------------|
| 锚点 | 实现代码或工具脚本引用、至少三个其他工作区文档引用，或 README 速读路径 / 规范点名的文档，永不自动降级；自区引用不计 |
| 活跃 | 新文档默认活跃；最近更新或引用在 21 天内，保留全文 |
| 折叠 | 非锚点且最近更新、引用均超过 21 天时复核；仍有至少两处跨区引用则保留全文并说明，否则原位改为摘要 |
| 边缘 | 非锚点且两日期均超过 90 天时复核；沿用跨区引用检查，原位改为简短骨架，目录移到根文档末尾的历史材料位置 |

时间阈值只触发复核，不自动判定材料失去价值；锚点优先。默认阈值 21 / 90 天、跨区锚点三处，可按项目约定调整。

每次创建或更新工作区，按需执行一次体检：

1. 用 `git log -1 --format=%ci -- <文件>` 查拆分文档最近修改，用 `rg` 查跨区引用；排除本工作区、开发日志、归档，按实际代码目录检查锚点。
2. 核对日期与分层条件。新增 / 更新链接时刷新被引用文档的最近引用日期，并同步根目录记录。
3. 折叠或边缘处理前确认全文已有可恢复的 Git 历史；无可恢复历史则保留全文。摘要保存结论、保留理由、关键决定、原位置与恢复方式；骨架至少保存一句结论与恢复方式。
4. 用户点名折叠或边缘材料时，从历史恢复全文并改回活跃。首次建区没有可供压缩的历史，不做降级。
5. 根文档目录记录状态，收敛计划末尾集中记录体检日期与结果，顶层 README 只同步简短摘要。

整区收官或路线冻结由 `archive-workspace` 承接，体检不自行归档、删文件或迁移资产。

## 完成前检查

核对正文与进度是否一致、链接是否可达、历史与当前条件是否分清；确认建议没有被写成已决定、文档检查没有被写成产品实测。运行 `git diff --check`，遵守项目验证要求，不编写产品实现代码。

交付时先讲本轮内容上的变化和还需解决的问题，再给阅读入口与检查结果。有分层调整时说明处理与恢复方式；没有变化时不逐项播报篇数、锚点和无操作清单。
